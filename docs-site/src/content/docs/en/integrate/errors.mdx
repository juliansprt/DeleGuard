The most expensive mistake is treating `DENY` as “the API failed” and **retrying the tool**. Do not.

## Status table

| HTTP | `error` | Meaning | Agent action |
| --- | --- | --- | --- |
| 200 | — | Evaluated decision (`ALLOW` / `DENY` / `REQUIRE_APPROVAL`) | Follow `decision`. |
| 400 | `invalid_request` | Schema or missing `Idempotency-Key` | Fix the request; do not execute. |
| 401 | `invalid_agent_credential` / `unauthorized` | Bad key or wrong credential type | Do not execute. Check `dgk_` vs `dgc_`. |
| 401 | `console_authentication_required` | Called a console endpoint without a human token | Use `dgc_` / cookie, not the agent key. |
| 404 | `not_found` | Decision/approval/policy missing in this tenant | Do not execute. |
| 409 | `conflict` | Idempotency-Key reused with a different body, or incompatible state | Do not assume ALLOW. Re-read the original decision. |
| 503 | `authorization_unavailable` | Postgres or PDP down | **Fail closed**: do not execute. Retry authorize, never the tool. |
| 500 | `internal_error` | Unexpected failure | Fail closed. |

<Aside type="danger" title="Fail closed">
503 and 5xx are **not** a soft DENY or an ALLOW. If no decision was persisted, the action does not happen.
</Aside>

## Idempotency

- Mint an `Idempotency-Key` **per action attempt** (e.g. a UUID bound to `invoiceId` + `intentId`).
- If HTTP drops, **resend the same** header and body.
- Changing the body with the same key yields **409**.

## Timeouts

Authorize with a short timeout (1–3 s). If it expires:

1. Do not execute the tool.
2. Retry authorize with the same idempotency key.
3. If Deleguard is still down, abort the agent turn.

## Expired approvals

If the human does not respond in time, the worker marks the approval expired. A later `GET /v1/decisions/{id}` does not turn that into ALLOW. The agent must authorize again (new key) if the business allows it.
